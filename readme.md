# Симулятор автоматизированной парковки

Вторая часть реализована в `part2/`: каждый участник модели — автомобиль, диспетчер, генератор прибытий — работает в отдельном потоке (`pthread`). Потоки взаимодействуют через мьютекс и семафоры. Однопоточная версия первого задания описана в [report1.md](report1.md), многопоточная — в [report2.md](report2.md).

В третьей части реализованы четыре варианта: два с дочерними процессами и два с независимо запускаемыми программами. Обмен данными организован через POSIX-разделяемую память или очереди сообщений; синхронизация — через семафоры. Устройство и результаты — в [report3.md](report3.md).

## Структура проекта

| Папка | Содержимое |
|---|---|
| `part2/src/`, `part2/include/` | Исходники и заголовки рабочей многопоточной версии |
| `part2/tests/` | Её тестовые наборы, проверка журнала и скрипт запуска |
| `part3/common/` | Модель, параметры, очередь индексов, стратегии, часы, интерфейс, POSIX-память и общая логика дочерних процессов |
| `part3/fork_unnamed/` | Рабочий вариант с дочерними процессами, POSIX-разделяемой памятью и неименованными семафорами (4–5 баллов) |
| `part3/fork_named/` | Рабочий вариант с дочерними процессами, POSIX-разделяемой памятью и именованными семафорами (6 баллов) |
| `part3/independent_shm/` | Рабочие независимые программы с POSIX-разделяемой памятью и именованными семафорами (7–8 баллов) |
| `part3/independent_mq/` | Рабочие независимые программы с POSIX-очередями сообщений и именованными семафорами (выше 8 баллов) |
| `part3/scripts/`, `part3/tests/` | Запуск и тестирование четырёх вариантов |
| `build/bin/` | Исполняемые файлы, разложенные по реализациям (вне Git) |

В каждой реализации третьей части есть `src/`, `include/` и `CMakeLists.txt`.
Общие модули находятся в `part3/common/`. CMake собирает программы;
запуск выполняется отдельными командами или скриптами. Для независимых вариантов предусмотрены ручной запуск из разных терминалов и общий сценарий демонстрации.

## Требования к окружению
Для успешной сборки и запуска приложения потребуются:
*   ОС: Linux (WSL)
*   Компилятор: `gcc` (C11, библиотека `pthread`)
*   Системы сборки: `cmake` и `make`

Для полного набора тестов третьей части также нужны Bash, AWK, Python 3.9+,
утилита `timeout`, доступ к `/proc` и `/dev/shm`. Тестовая библиотека подмены
системных вызовов собирается тем же C-компилятором (`cc` или переменная `CC`).

## Инструкция по сборке

Выполните следующие команды в корневой директории проекта:

```bash
cmake -S . -B build
cmake --build build
```
Сейчас собираются вторая часть `build/bin/part2/parking_sim` (цель `parking_sim`)
и варианты третьей части: `build/bin/fork_unnamed/parking_fork_unnamed`
и `build/bin/fork_named/parking_fork_named` (одноимённые цели CMake).
Программы независимого сеанса находятся в `build/bin/independent_shm/`.
Комплект с очередями сообщений находится в `build/bin/independent_mq/` (цель `parking_independent_mq`).
Все команды ниже выполняются из корня проекта.

## Третья часть: fork_unnamed

```bash
# Обычный запуск с длительностью такта 800 мс
./build/bin/fork_unnamed/parking_fork_unnamed

# Быстрый прогон до обработки всех автомобилей
./build/bin/fork_unnamed/parking_fork_unnamed -d 1 -t 0 -R 7 -L parking_result.txt

# Сценарий запуска из любой рабочей директории
part3/scripts/run_fork_unnamed.sh -d 100 -g short -q 10 -w 20

# Полный набор тестов этого варианта
part3/tests/run_tests.sh fork_unnamed
```

Поддерживаются те же флаги модели, что и во второй части (описаны ниже).
У третьей части путь журнала по умолчанию — `parking_result.txt` относительно
текущей директории. Скрипт запуска задаёт путь в корне репозитория; его можно
переопределить собственным `-L`.

Родитель генерирует прибытия и создаёт все дочерние процессы: диспетчера,
отрисовщик и по одному процессу на автомобиль. Общее состояние расположено
в POSIX-разделяемой памяти, доступ защищает бинарный семафор. Именованных
семафоров и потоков в этой реализации нет. Имя памяти удаляется сразу после
`mmap`; дочерние процессы наследуют отображение. Все семафоры уничтожаются
после сбора детей через `waitpid`, отображение освобождается через `munmap`.

Завершение: все автомобили обработаны, достигнут лимит `-t`, получен `SIGINT`
или `SIGTERM`. При остановке очередь отменяется, стоянки прерываются, выводятся
итоговая статистика и причина. При аварии ребёнка остальные дети завершаются
и собираются; программа возвращает 1 без итоговой статистики по неполному состоянию.
Ошибка открытия журнала или создания ресурсов также даёт код 1.

Журнал содержит параметры парковки и все события. Строки «Генерация» позволяют
сравнить случайные входные значения при одинаковом `-R`; порядок конкурентных
событий и итоговая статистика могут различаться.

Тесты: **37 проверок сценариев/аргументов/сигналов и 20 проверок процессов и IPC**.
Проверяются все четыре инварианта, сбор детей, два одновременных запуска,
очистка ресурсов и откат при ошибках системных вызовов. Журналы сценариев лежат
в `part3/tests/logs/fork_unnamed/`; переменная `PARKING_TEST_LOGS` меняет каталог.
Дополнительные IPC-тесты используют временную папку в `/tmp`.

Проверка памяти и неопределённого поведения:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DSANITIZE=address,undefined
cmake --build build-asan --target parking_fork_unnamed
PARKING_SKIP_FAULTS=1 part3/tests/run_tests.sh ./build-asan/bin/fork_unnamed/parking_fork_unnamed
```

Этот прогон выполняет 45 проверок. Подмена системных вызовов через `LD_PRELOAD`
проверяется на обычной сборке отдельно от санитайзера. TSan предназначен для
потоков; межпроцессную синхронизацию здесь проверяют сценарии и журнал.

## Третья часть: fork_named

```bash
cmake --build build --target parking_fork_named
./build/bin/fork_named/parking_fork_named -d 100 -t 0 -R 7 -L parking_named_result.txt

# Скрипт с теми же параметрами модели
part3/scripts/run_fork_named.sh -d 100 -g short -q 10 -w 20

# Только именованный вариант или все реализованные варианты подряд
part3/tests/run_tests.sh fork_named
part3/tests/run_tests.sh
```

Роли процессов, интерфейс, параметры, очередь и завершение совпадают с `fork_unnamed`.
Общий код участников находится в `part3/common/src/fork_processes.c`, обёртки
синхронизации — в `fork_sync.c`, размещение данных — в `shared_memory.c`.
Отдельные модули реализаций отвечают за создание и освобождение семафоров.

В `fork_named` родитель создаёт N + 3 именованных семафора через
`sem_open(O_CREAT | O_EXCL, 0600, значение)`: общую блокировку, два уведомления
и персональный ответ каждому автомобилю. В отображении данных модели нет `sem_t`.
Указатели на открытые семафоры хранятся локально. Имя каждого семафора удаляется
через `sem_unlink` сразу после открытия; `fork` наследует открытые объекты.
Каждый ребёнок при штатном выходе закрывает унаследованные семафоры через `sem_close`,
родитель делает это после сбора детей. При частичной ошибке закрываются только
успешно открытые объекты; чужое имя после ошибки `O_EXCL` не удаляется.

В `independent_shm` имена сохраняются до завершения работы участников.
`fork_named` использует наследование через `fork`.

Тесты именованного варианта: **37 сценариев и 24 проверки процессов и IPC — всего 61**.
Включены ошибки `sem_open` и `sem_unlink`, проверка прав и начальных значений,
удаление имён, закрытие объектов во всех процессах, отсутствие `sem_init`,
сохранение чужого семафора при совпадении имени. Для `fork_unnamed` после выделения
общего кода повторно пройдены все 57 проверок. Логи разделены по каталогам
`part3/tests/logs/fork_named/` и `part3/tests/logs/fork_unnamed/`.
При `all` переменная `PARKING_TEST_LOGS` задаёт общий родительский каталог для них.

ASan/UBSan для обоих вариантов выполняет по 45 проверок без подмены системных вызовов:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DSANITIZE=address,undefined
cmake --build build-asan --target parking_fork_unnamed parking_fork_named
PARKING_SKIP_FAULTS=1 part3/tests/run_tests.sh ./build-asan/bin/fork_named/parking_fork_named
PARKING_SKIP_FAULTS=1 part3/tests/run_tests.sh ./build-asan/bin/fork_unnamed/parking_fork_unnamed
```

Текущая проверка прошла внутри песочницы с `ASAN_OPTIONS=detect_leaks=0:halt_on_error=1`
и `UBSAN_OPTIONS=halt_on_error=1`: ограничения ptrace мешают LeakSanitizer, а запуск
вне песочницы не был разрешён. Утечки памяти после выделения общего кода через LSan
не проверены; очистка IPC и вызовы `sem_close` проверены отдельными тестами.

## Третья часть: independent_shm

Собрать весь комплект этого варианта и запустить одной командой:

```bash
cmake -S . -B build
cmake --build build --target parking_independent_shm
part3/scripts/run_independent_shm.sh -d 100 -t 0 -R 7
part3/tests/run_tests.sh independent_shm
```

В `build/bin/independent_shm/` собраны четыре C-программы:

| Программа | Назначение |
|---|---|
| `parking_dispatcher СЕАНС [флаги модели]` | Создаёт сеанс, обслуживает очередь, показывает табло, управляет остановкой и удалением ресурсов |
| `parking_car СЕАНС НОМЕР` | Самостоятельно подключается к сеансу, моделирует один автомобиль |
| `parking_arrivals СЕАНС` | По запланированным интервалам запускает внешнюю программу автомобиля через `posix_spawn` и собирает своих детей |
| `parking_independent_shm [флаги модели]` | Необязательный запускатель: создаёт уникальное имя, запускает диспетчера и генератор, передаёт сигнал и ждёт их завершения |

Диспетчер и автомобиль можно запускать вручную из разных терминалов:

```bash
# Терминал 1, из корня проекта: сеанс demo, два обычных автомобиля
./build/bin/independent_shm/parking_dispatcher demo -t 0 -d 100 -r 1 -l 0 -s 0 -c 2 -C 0 -S 0 -L parking_demo.txt

# Терминал 2, из корня проекта
./build/bin/independent_shm/parking_car demo 1

# Терминал 3, из корня проекта
./build/bin/independent_shm/parking_car demo 2
```

Для автоматического потока прибытий запустите `parking_arrivals demo` вместо
ручного запуска автомобилей. Можно выполнить команды из разных рабочих директорий,
используя абсолютные пути к бинарникам. Общий журнал диспетчер записывает в параметры
как абсолютный путь, все участники открывают его с `O_APPEND`.

Имя сеанса: 1–48 латинских букв, цифр, `_` или `-`. Номера автомобилей — от 1
до заданной суммы `-c/-C/-S`, каждый номер используется один раз. Тип, время стоянки
и интервал заранее вычисляются по seed. Имена POSIX-памяти и N+2 семафоров сохраняются
до завершения сеанса; участники открывают их самостоятельно, без наследования отображений.
Счётчики, индексы и смещения находятся в общей памяти, указатели остаются локальными.

Сначала диспетчер ожидает подключения; часы модели запускает первый автомобиль или
генератор. Для нулевого числа автомобилей диспетчер завершает сеанс сразу,
без ожидания генератора. Подключение к отсутствующему диспетчеру
ожидается не более 5 с. Запуск второго владельца с тем же именем, второго активного
генератора или повторного номера автомобиля отклоняется.

SIGINT/SIGTERM можно отправлять диспетчеру, автомобилю, генератору или запускателю:
они инициируют остановку всего сеанса. При лимите времени/сигнале регистрация закрывается,
очередь отменяется, автомобили освобождают места. Генератор собирает своих детей,
участники отключаются, владелец удаляет имена и закрывает ресурсы. При обнаруженной
ошибке участника сеанс завершается с кодом 1 без недостоверной итоговой статистики.

Тесты: **37 сценариев и 28 проверок независимого запуска/IPC, всего 65**.
Проверены ручное подключение, порядок запуска, разные cwd, существующие и повреждённые
сеансы, повторные подключения, сигналы, параллельные сеансы, seed и ошибки запуска/очистки.
После выделения общего диспетчера повторно пройдены 57 и 61 проверка fork-вариантов.
Эти три варианта вместе проходят **183 проверки**.

ASan/UBSan без LD_PRELOAD — 53 проверки этого варианта:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DSANITIZE=address,undefined
cmake --build build-asan --target parking_independent_shm
ASAN_OPTIONS=detect_leaks=0:halt_on_error=1 UBSAN_OPTIONS=halt_on_error=1 PARKING_SKIP_FAULTS=1 part3/tests/run_tests.sh ./build-asan/bin/independent_shm/parking_independent_shm
```

Нужен `/proc/self/exe` для поиска соседних программ генератором и запускателем.
Python требуется только тестам.

## Третья часть: independent_mq (выше 8 баллов)

```bash
cmake -S . -B build
cmake --build build --target parking_independent_mq
part3/scripts/run_independent_mq.sh -d 100 -t 0 -R 7
part3/tests/run_tests.sh independent_mq
```

В `build/bin/independent_mq/` находятся `parking_dispatcher`, `parking_car`,
`parking_arrivals` и запускатель `parking_independent_mq`. Их роли и аргументы
совпадают с вариантом `independent_shm`; это отдельные исполняемые программы.
Ручная демонстрация в трёх терминалах:

```bash
# Терминал 1
./build/bin/independent_mq/parking_dispatcher demo -t 0 -d 100 -r 1 -l 0 -s 0 -c 2 -C 0 -S 0 -L parking_mq_demo.txt
# Терминал 2
./build/bin/independent_mq/parking_car demo 1
# Терминал 3
./build/bin/independent_mq/parking_car demo 2
```

Для автоматических прибытий используйте `parking_arrivals demo` вместо ручных
автомобилей. Каждый номер 1..N используется один раз. Генератор запускает все
номера с первого, поэтому ручной запуск и генератор в одном сеансе не смешиваются.
Имя сеанса имеет тот же формат: 1–48 букв ASCII, цифр, `_` и `-`.

Состояние парковки хранится только у диспетчера, который также пишет журнал и
рисует табло. Команды и ответы передаются через две POSIX-очереди
`/parking_mq_СЕАНС_requests` и `/parking_mq_СЕАНС_replies`. Четыре именованных
семафора обеспечивают готовность сеанса, исключительный доступ к маршрутизации
ответов и уведомления о запросах/ответах. Все клиенты открывают объекты по именам;
разделяемая память для данных модели не используется.

В каждой очереди максимум 10 сообщений. Диспетчер сохраняет ожидающие отправки
ответы локально, продолжая принимать освобождения мест и сигналы остановки.
Получатель выбирает ответ по PID и идентификатору подключения, сохраняя порядок
остальных сообщений. Это позволяет обслуживать сотни автомобилей с двумя очередями.
Нужна поддержка POSIX MQ в ядре Linux; монтирование `/dev/mqueue` для работы и тестов
не требуется. При недоступном IPC программа сообщает ошибку с кодом 1.

Часы запускаются первым участником. Завершение — все автомобили обработаны,
лимит `-t`, SIGINT или SIGTERM любому участнику. Очередь отменяется, стоянки
прерываются, участники подтверждают выход. Диспетчер удаляет собственные очереди
через `mq_unlink`, семафоры через `sem_unlink`; процессы закрывают дескрипторы.
Частичная ошибка создания не удаляет чужие объекты. SIGKILL владельцу не позволяет
выполнить очистку: для следующего запуска следует использовать новое имя сеанса.

Тесты: **37 общих сценариев + 34 проверки независимых процессов и IPC = 71**.
Включены порядок адресованных ответов, нагрузка 500 автомобилей, переполнение,
неверные размер/версия сообщений, отсутствие обмена через `shm_open`, ошибки
создания/отправки/получения/удаления и очистка ресурсов. Все четыре реализации
вместе: **254 проверки**. Прогон ASan/UBSan без LD_PRELOAD — 57 проверок MQ-варианта:

```bash
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DSANITIZE=address,undefined
cmake --build build-asan --target parking_independent_mq
ASAN_OPTIONS=detect_leaks=0:halt_on_error=1 UBSAN_OPTIONS=halt_on_error=1 PARKING_SKIP_FAULTS=1 part3/tests/run_tests.sh ./build-asan/bin/independent_mq/parking_independent_mq
```

`detect_leaks=0` отключает LSan по указанному выше ограничению среды.
Общий тестовый запуск всех четырёх вариантов: `part3/tests/run_tests.sh all`.

## Вторая часть: запуск программы

Вы можете запустить симуляцию с параметрами по умолчанию или гибко настроить их через аргументы командной строки.

### Базовый запуск
```bash
./build/bin/part2/parking_sim -L parking_result.txt
```

### Запуск с пользовательскими параметрами
Программа поддерживает настройку всех ключевых переменных через флаги командной строки.

**Пример теста (много машин, мало мест, долгая стоянка):**
```bash
./build/bin/part2/parking_sim -L parking_result.txt -t 200 -q 5 -r 1 -l 1 -s 0 -p 15 -P 30 -c 20
```

**Доступные аргументы:**
*   **Длительность симуляции:**
    *   `-t `: Предельное число тактов симуляции (по умолчанию: 100). `-t 0` — без ограничения: симуляция идёт, пока не будут обработаны все автомобили, или до Ctrl+C.
    *   `-d `: Длительность одного такта в миллисекундах (по умолчанию: 800). Например, `-d 1` — почти мгновенный прогон.
*   **Воспроизводимость и стратегия:**
    *   `-R `: Начальное значение генератора случайных чисел (по умолчанию: текущее время). Seed выводится на экран и в лог. При одинаковом seed и параметрах повторяются все случайные величины (типы автомобилей, интервалы прибытия, время стоянки), но порядок событий в журнале может немного отличаться: он зависит от того, как ОС переключает потоки.
    *   `-g `: Стратегия, по которой диспетчер выбирает из очереди автомобиль на освободившееся место (среди машин подходящего типа):
        *   `fifo` (по умолчанию) — дольше всех ждущий;
        *   `lifo` — последний вставший в очередь;
        *   `random` — случайный;
        *   `short` — с самым коротким временем стоянки (место быстрее освободится для следующих).
*   **Журнал:**
    *   `-L `: Путь к файлу журнала (по умолчанию: `../parking_result.txt`).
*   **Инфраструктура парковки:**
    *   `-q `: Максимальная вместимость очереди (по умолчанию: 3).
    *   `-r `: Количество мест для *Обычных* авто (по умолчанию: 2).
    *   `-l `: Количество мест для *Крупногабаритных* авто (по умолчанию: 1).
    *   `-s `: Количество мест для *Специальных* авто (по умолчанию: 1).
*   **Генерация трафика (пул автомобилей):**
    *   `-c `: Количество генерируемых *Обычных* авто (по умолчанию: 15).
    *   `-C `: Количество генерируемых *Крупногабаритных* авто (по умолчанию: 12).
    *   `-S `: Количество генерируемых *Специальных* авто (по умолчанию: 10).
*   **Поведенческие таймеры:**
    *   `-a ` / `-b `: Мин. и макс. интервал между прибытиями машин в тактах (по умолчанию: 0 и 2; 0 — несколько машин приезжают одновременно).
    *   `-p ` / `-P `: Мин. и макс. продолжительность стоянки (по умолчанию: 7 и 10).
    *   `-w `: Максимальное время ожидания машины в очереди до ухода (по умолчанию: 8).

## Взаимодействие и интерфейс

В процессе работы программа выводит на экран динамический текстовый дашборд.
*   **Альтернативный буфер:** Интерфейс отрисовывается в альтернативном буфере терминала, поэтому после завершения работы история ваших команд не будет засорена.
*   **Безопасное прерывание (Ctrl+C):** Программа корректно обрабатывает сигналы `SIGINT` (Ctrl+C) и `SIGTERM` (`kill <pid>`). При прерывании автомобили в очереди получают отмену, припаркованные досрочно уезжают, все потоки завершаются, после чего программа сохраняет логи и выводит итоговую статистику.

## Условия завершения
1.  Все автомобили обработаны (обслужены, ушли из очереди или получили отказ).
2.  Истёк лимит времени `-t` (при `-t 0` лимита нет).
3.  Получен сигнал `SIGINT` (Ctrl+C) или `SIGTERM`.

Причина завершения выводится в итоговой статистике.

## Логирование и результаты

В примерах выше журнал **`parking_result.txt`** создаётся в корневой папке благодаря `-L parking_result.txt`.
Без этого флага сохранён прежний путь `../parking_result.txt`, отсчитываемый от текущей рабочей директории, а не от расположения исполняемого файла.
В нем содержится:
1.  Хронология всех событий с номером такта: прибытие, постановка в очередь, назначение места, начало и окончание стоянки, освобождение места, уход из очереди, отказ.
2.  Итоговая статистика обслуженных и потерянных клиентов.

Для просмотра лога используйте утилиту `cat` или `less`:
```bash
cat parking_result.txt
```

## Тестирование

В папке `part2/tests/`:
*   `cases.txt` — тестовые наборы параметров с ожидаемым исходом (обработка всех авто, лимит времени, ошибка в параметрах);
*   `check_log.awk` — проверка журнала: инварианты (место не занято двумя авто, авто не находится одновременно в очереди и на месте, очередь не переполнена), допустимый порядок событий для каждого авто и совпадение итоговой статистики с журналом;
*   `run_tests.sh` — прогоняет все наборы (такт 1 мс), а также проверяет завершение по `SIGINT` и `SIGTERM`.

```bash
# из корня проекта, после сборки в build/
part2/tests/run_tests.sh
# или с указанием исполняемого файла
part2/tests/run_tests.sh путь/к/parking_sim
```
Журналы прогонов сохраняются в `part2/tests/logs/` (`01.txt`, `02.txt`, ... — по номеру теста).

Для поиска гонок данных и ошибок памяти проект можно собрать с санитайзером и прогнать те же тесты:
```bash
cmake -S . -B build-tsan -DSANITIZE=thread     # или -DSANITIZE=address
cmake --build build-tsan
part2/tests/run_tests.sh ./build-tsan/bin/part2/parking_sim
```
