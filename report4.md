**Выполнил:** Серебряков Владимир Романович, БПИ252. **Вариант:** 26 — автоматизированная парковка.

## Статус

Добавлены четыре программы, восстановление клиентов, несколько наблюдателей,
скрипты, Dockerfile, Compose и проверки на накопительные требования выше 8 баллов.
Пройдены сборка, модульные проверки, **26 реальных TCP-тестовых методов** на обычной

Docker-образ собран, контейнерная приёмка с восстановлением клиентов выполнена.

## Условие

Общая задача — `task1.txt`: три типа автомобилей и совместимых мест, ограниченная очередь,
случайные интервалы прибытия и стоянки, ограничение ожидания, выбранная стратегия назначения.
Наблюдаемые события: прибытие, очередь, назначение, начало/окончание стоянки, освобождение,
отказ/таймаут и итоговая статистика. Четыре инварианта: уникальность назначения места,
совместимость типов, отсутствие автомобиля одновременно в очереди и на месте, соблюдение вместимости.
Завершение — обработка заданного числа автомобилей, лимит моделирования или сигнал серверу.

`task4.txt` добавляет сетевое взаимодействие самостоятельных программ на C, IP/порт из CLI,
работу на разных компьютерах, отдельного наблюдателя, множество наблюдателей, восстановление
рабочих клиентов и завершение подключённых клиентов вместе с сервером.

## Принятые решения

- TCP, сервер с неблокирующими сокетами и `poll`. Предметные модули очереди, стратегий,
  диспетчера, ГСЧ, часов и UI переиспользуются из третьей части без изменения её целей.
- Единственный владелец модели — сервер. Автомобиль сообщает номер/тип и получает решения;
  генератор запускает внешние клиенты; наблюдатели показывают полученное от сервера табло.
- Принятое прибытие живёт независимо от TCP-соединения. Назначение сразу начинает стоянку;
  сервер учитывает её срок даже при обрыве до получения ответа. Это исключает вечную бронь.
  Клиент отсчитывает полученный остаток и сообщает об отъезде; ранний запрос не освобождает место.
- Переподключение того же номера восстанавливает состояние; повтор ARRIVE не учитывается заново.
  Ожидание и стоянка не продлеваются. Два активных соединения одного номера запрещены.
  Клиент после первого STATE отправляет ARRIVE только для ещё не прибывшего автомобиля;
  восстановленные очередь/стоянка/конечный результат не требуют повторной команды.
- Все сроки относятся к монотонным часам сервера. Клиент получает остаток длительности, а не
  абсолютное время другого компьютера. Наблюдатель не запускает часы моделирования.
- Один формат кадров: 16 байтов заголовка (magic/версия, тип, размер, seq — uint32 в сетевом
  порядке), затем UTF-8/ASCII текст указанной длины. C-структуры и указатели по сети не передаются.
- Docker дополняет обычные бинарники. После разрешения внешнего запуска проверены
  образ и контейнерный сценарий. Контейнеры одного хоста не считаются двумя компьютерами.

## Сценарий: сущности и процессы

| Сущность | Программа / данные | Поведение |
|---|---|---|
| Диспетчер | `parking_server IP ПОРТ [флаги]` | Принимает подключения, обрабатывает команды и сроки, назначает места, пишет журнал |
| Автомобиль | `parking_car АДРЕС ПОРТ НОМЕР` | Получает план, сообщает номер/тип, ожидает решения, отсчитывает остаток стоянки, сообщает об отъезде |
| Дорога | `parking_arrivals АДРЕС ПОРТ` | Получает планы, через интервалы запускает внешние автомобили через posix_spawn, собирает собственных детей |
| Табло | `parking_monitor АДРЕС ПОРТ` | Получает согласованный снимок и отображает комплексное состояние |
| Места и очередь | Локальные массивы сервера | Не имеют отдельного поведения; содержат индексы автомобилей |

Сервер не создаёт клиентов. Генератор и ручной запуск автомобилей — способы
создать сетевых участников; их процессы могут находиться на другом компьютере.
Генератор ищет соседний бинарник автомобиля через `/proc/self/exe`, поэтому четыре
исполняемых файла поставляются одним каталогом. Потоки pthread не создаются.

Все сокеты неблокирующие. Один серверный цикл `poll` последовательно изменяет
модель; блокировок общей памяти между компьютерами нет. В каждой итерации ограничено
число принятых соединений, разобранных сообщений и объём отправки одному клиенту,
чтобы один участник не занял весь цикл. Сроки проверяются между обработками событий.

## Протокол

Заголовок кадра — четыре uint32 в сетевом порядке байтов: magic `0x504b3401`
(последний байт — версия 1), тип, длина полезной части, номер команды seq.
Далее идут ровно length байтов текста UTF-8/ASCII, без встроенного NUL.
Числовые поля разделяются пробелами и разбираются с проверкой переполнения.
Роли: 1 — автомобиль, 2 — генератор, 3 — наблюдатель. У автомобиля id от 1 до N,
у остальных id=0. В сообщениях нет C-структур, PID или абсолютных адресов памяти.

| Сообщение | Полезная часть и смысл |
|---|---|
| HELLO | role id; регистрация соединения |
| WELCOME | id type tick_ms total_cars seed session; параметры и экземпляр сервера |
| ARRIVE | id type; фактическое прибытие, проверяемое по плану |
| STATE | id type status spot parking_ticks remaining_ms server_tick |
| LEAVE | Пусто; сообщение клиента об окончании; ранняя команда не освобождает место |
| PLAN / PLAN_REPLY | Номер / id interval arrived finished active; генератор узнаёт, какие номера остались |
| SNAPSHOT | Полный текст общего табло, сформированный из согласованной модели |
| PING / PONG | Уведомления активности соединения |
| DETACH / ACK | Штатное отключение одного участника |
| STOP / ACK | Причина и итоговая статистика / подтверждение завершения |
| ERROR | Причина отклонения команды или регистрации |

Команды соединения имеют возрастающие ненулевые seq. Ответ сохраняет номер
команды, уведомления сервера имеют seq=0. Повтор ARRIVE с новым номером команды
или на новом соединении возвращает прежнее состояние и не меняет счётчики.
Повтор уже использованного seq отклоняется. Это разные случаи: повтор операции
допустим, нарушение последовательности кадров одного соединения — нет.

Декодер накапливает неполный кадр и извлекает несколько готовых кадров в исходном
порядке. Отправка хранит смещение частично переданного кадра. EINTR и EAGAIN
не теряют данные; MSG_NOSIGNAL позволяет обрабатывать разрыв как ошибку сокета.
Сервер принимает полезную часть до 512 байтов, клиент — до 1 МиБ; очередь исходящих
данных одного соединения ограничена 2 МиБ, соединений до 1024. Новый периодический
снимок не ставится, пока предыдущий ещё отправляется. Зависшее или неактивное
соединение отключается по сроку 5 с. Это не останавливает предметную модель.

Наблюдатель получает готовое табло по сети и не читает журнал или память сервера.
На экране — места, очередь, статистика, seed, стратегия, такт, три последних события.
Начальный снимок отправляется при HELLO, последующие — с периодом такта,
ограниченным диапазоном 50..500 мс. Формирование кадра выполняется тем же процессом,
который владеет моделью, поэтому смешанных состояний мест и очереди не возникает.

## Время и восстановление

Приветствие автомобиля ещё не является прибытием. ARRIVE отдельно передаёт номер
и тип; сервер проверяет их. Первый ARRIVE или генератор запускает часы. Наблюдатели
не влияют на начало. При N=0 сервер завершает модель сразу. В ручном режиме с `-t 0`
нужно запустить все заданные номера либо остановить сервер сигналом.

Диспетчер назначает место и фиксирует начало стоянки в одной операции. Отдельного
подтверждения START нет: обрыв после назначения не создаёт зависшее резервирование.
Автомобиль получает остаток времени, моделирует ожидание без блокировки остальных
и посылает LEAVE. Сервер также освобождает место по собственному сроку, если клиент
отключён или его сообщение опоздало. Ранний LEAVE только возвращает состояние.

После отключения сохраняются место/позиция в очереди, deadline, park_end и конечный
результат. Сервер продолжает учитывать сроки. Повторная регистрация того же номера
возвращает состояние, а повтор ARRIVE не сбрасывает часы, ожидание или статистику.
Если исходный клиент ещё активен, второй отклоняется. Обрыв выявляется по EOF/ошибке
либо сроку активности. Пользователь может вновь запустить клиент; бесконечных
автоматических попыток восстановления нет.

Генератор запрашивает план каждого номера: завершённые и активные пропускаются,
отключённые прибывшие восстанавливаются без нового интервала, ещё не прибывшие
выпускаются с плановым интервалом. Поэтому перезапуск генератора не создаёт
второе прибытие. При сигнале он собирает только собственных детей.

## Обеспечение инвариантов

| Инвариант | Обеспечение |
|---|---|
| Одно место — одному автомобилю | Единственный сервер ищет свободное место и сразу назначает его |
| Совместимость | Общие find_free_spot/pick_car сравнивают типы |
| Авто не в очереди и на месте одновременно | Общий dispatcher удаляет индекс из очереди перед назначением, в одном проходе сервера |
| Вместимость не превышена | enqueue отклоняет заполненную очередь, назначаются только существующие свободные места |

Перед раздачей мест сервер удаляет автомобили с истёкшим ожиданием. Завершение
машины защищено отдельным finished, поэтому повтор операции не удваивает итог.
Журнал содержит заголовок параметров и прежние события: его проверяет фактический
`part3/tests/check_log.awk`, включая совместимость и баланс статистики.

## Интерфейс и завершение

Базовый режим не содержит общего табло: сервер сообщает собственные принятые
события, автомобиль показывает только свой статус. Отдельный монитор представляет
уровни 6–8. В терминале он использует альтернативный буфер и ANSI; при `--plain`
или выводе в файл удаляет CSI-последовательности. Последняя статистика сохраняется
после выхода из альтернативного буфера. Ввод-вывод выполняется через дескрипторы:
open/write/close и socket/send/recv; snprintf служит только форматированию строк.

| Условие | Реакция |
|---|---|
| Все N автомобилей получили конечный результат | Штатная остановка сервера |
| Достигнут лимит -t | Отмена ожидания, досрочное освобождение мест |
| SIGINT/SIGTERM серверу | Та же остановка с причиной в статистике |
| SIGINT/SIGTERM клиенту | DETACH, выход только этого клиента |
| Пропал клиент | Сохраняется модель, остальные продолжают работу |
| Пропал сервер | Клиенты выходят с ошибкой при разрыве или сроке активности |

При штатной остановке сервер закрывает регистрацию новых прибытий, отменяет очередь,
освобождает места и записывает финальную статистику. Затем отправляет финальное
состояние и STOP подключённым ролям, принимает ACK и закрывает соединения.
Ожидание завершения ограничено 2 с. Принимающий сокет закрывается после этой фазы:
ещё подключающиеся дети получают STOP даже до HELLO. Они не регистрируют новые
прибытия. Генератор останавливает/собирает собственных детей и только затем
подтверждает STOP, поэтому сервер не обрывает их подключения преждевременно.
При зависании собственного ребёнка после ограниченного ожидания генератор использует
SIGKILL и waitpid. У сетевого сервера нет чужих PID для kill.

## Структура и запуск

`part4/src/net.c` — кодирование и сокеты; `client.c` — клиентский цикл, сигналы
и heartbeat; `model.c` — локальная модель, сроки и журнал; `session.c` — роли,
регистрация, команды и финальные уведомления; `server.c` — poll и запуск.
`car_client.c` — проверяемое поведение автомобиля, `car.c`, `arrivals.c`, `monitor.c` —
точки входа самостоятельных клиентов. Заголовки — в
`part4/include/`. Сборка — цель `parking_tcp`, проверки — `parking_tcp_checks`.
Исполняемые файлы — `build/bin/part4/`. Команды для всех уровней, Docker
и двух компьютеров приведены в [part4/README.md](part4/README.md).

## Фактические результаты и оставшаяся приёмка

  закодированы в памяти, реальные сетевые системные вызовы не выполняются.

  0 ошибок (26,969 с). В обоих случаях перед ними прошли четыре C-проверки и 28 ошибок CLI.

## Критическая оценка и исправления кода ИИ

1. Общее время из shared-memory решения нельзя переносить между хостами: сроки
   остались на сервере, в STATE передаётся остаток в миллисекундах.
2. Успешная отправка не доказывает обработку. При разрыве повтор ARRIVE безопасен;
   состояние и статистика принадлежат логическому автомобилю, не сокету.
3. Отдельный START создавал бы промежуток, в котором исчезнувший клиент мог навсегда
   удержать бронь. Назначение сразу начинает стоянку и устанавливает серверный срок.
4. ACK финального STOP изначально копировал seq=0 уведомления, хотя команды требуют
   ненулевой seq. Исправлен на следующий номер команды; проверяется тестом сеансов.
5. Статистика, напечатанная в альтернативном буфере монитора, исчезла бы при выходе.
   Клиент сохраняет итог и повторяет его после восстановления основного экрана.
6. Интервал генератора, полученный по сети, нельзя без проверки умножать на tick_ms.
   Добавлена проверка перед наносекундным умножением.
7. Обработчики команд выделены из основного poll-цикла в session.c: их можно проверять
   без доступных сокетов. Такая проверка не подменяет интеграционные тесты.
8. Модульные проверки первоначально не подтверждали реальную сетевую работу.
   После разрешения пользователя отдельно выполнены TCP-прогоны, ASan/UBSan,
   PTY и Docker; проверка двух физических хостов остаётся отдельным этапом.
9. В Release макрос NDEBUG отключал assert вместе с находившимися внутри тестовыми
   вызовами. Компиляция тестов падала на неиспользуемых переменных, а при отключении
   предупреждений тесты были бы недостоверны. Тестовые цели теперь получают -UNDEBUG
   и собираются отдельно от основных программ. Release-прогон выполнен успешно.
10. Поведение автомобиля выделено в car_client.c. После восстановления клиент теперь
    опирается на первый STATE и не отправляет ARRIVE для уже прибывшей машины.
11. Генератор учитывает PID только после успешного posix_spawn: значение выходного
    аргумента при ошибке не попадает в таблицу последующей очистки.
12. Первый реальный ASan-прогон обнаружил гонку штатной остановки: при лимите 20 мс
    некоторые дети генератора ещё выполняли HELLO и получали сброс/ERROR вместо STOP.
    Генератор теперь откладывает ACK до сбора детей, сервер принимает TCP-подключения
    в финальной фазе и отвечает STOP без регистрации прибытия. Добавлены модульные
    проверки отсроченного ACK и позднего HELLO, два сетевых метода, десять повторов
    короткого лимита. Окончательные полные прогоны прошли без ошибок.
